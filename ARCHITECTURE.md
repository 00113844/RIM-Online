# How RIM Online works

RIM Online is a Streamlit application that reimplements **RIM-2013b**, a bioeconomic model of
ryegrass management built in Excel and VBA. This document explains how the software is put
together and, more importantly, *why* it is put together that way.

For the rules an agent or contributor must follow, see [`CLAUDE.md`](CLAUDE.md). For current
status and next steps, see [`HANDOVER.md`](HANDOVER.md).

---

## 1. The governing idea

The Excel workbook is the specification. Python is an implementation of it.

That sounds obvious, but it was not how the project started, and the cost was severe. The
original `rim/` was written as an independent model that *resembled* RIM. Its numbers looked
plausible in isolation — which is precisely what made them dangerous. On the workbook's own
default first year it reported a gross margin of **$270.76/ha** against Excel's **$22.45/ha**.

Nothing about the Python code revealed this. It took building an oracle that could ask Excel
directly. Hence the two rules everything else follows from:

1. **Every calculation change starts from a citable source** — a formula (`Calcs!C167`), a VBA
   procedure, or a failing parity fixture. If you cannot cite one, you are guessing.
2. **Expected test values never come from Python.** They are captured from the workbook. A test
   whose expectations were generated by the code under test proves only that the code is
   self-consistent.

---

## 2. The workbook's shape

RIM-2013b looks like an intractable tangle of some 5,000 formulas. It is not. It is a **ten-column
vectorisation**: one spreadsheet column per simulation year, with the same formulas repeated
across all ten.

| Sheet | Year 1 | Year 10 | Contents |
|---|---|---|---|
| `2.Strategy` | `D` | `M` | The user's decisions, rows 4–19 |
| `Calcs` | `C` | `L` | ~370 rows of per-year intermediates |
| `Bio results` | `D` | `M` | Population and yield |
| `Eco results` | `E` | `N` | Revenue, costs, gross margin |

Years are joined by exactly one number: `Bio results!E11 = D20`. The seed left in the soil next
autumn becomes the next year's starting seed bank. Everything else about a year is computed from
that opening seed bank and the strategy chosen for the year.

So one Python function evaluating a single column, iterated ten times, reproduces the whole
workbook. That is what [`rim/calcs.py`](rim/calcs.py) is.

## 3. How the model works

### The season is not a single event

The insight the original Python port missed — and the reason it could never converge — is that
**ryegrass does not germinate all at once**. It emerges in five cohorts through autumn and winter,
and each control option catches only what has emerged by the time it is applied.

A pre-emergent herbicide sprayed at seeding cannot touch a plant that comes up six weeks later.
A post-emergent catches everything standing at the time but nothing still in the soil. Modelling
a year as one germinate → control → seed-set cycle cannot express any of this.

Two cascades therefore run down the season in parallel.

**The seed bank** is drawn down cohort by cohort (`Bio results` rows 11–16):

```
D11  end of summer          the seed bank carried in
D12  = D11 * (1 - g1)       what did not germinate in cohort 1
D13  = D12 * (1 - g2) * C159    ...cohort 2, then any ploughing burial
D14  = D13 * (1 - g3) * C160
D15  = D14 * (1 - g4)
D16  = D15 * (1 - g5) * (1 - loss)
```

**The plants** are what germinated, carried through each control and topped up by the next cohort
(rows 3–8):

```
D3  = D11 * g1                        cohort 1 emerges
D4  = D3 * C164 + D12 * g2 * C167     survivors + cohort 2
D5  = D4 * C165 + D13 * g3 * C167
D6  = D5 * C166 + D14 * g4 * C167
D7  = D6 * C168 + D15 * g5            post-emergent herbicides
D8  = D7 * C169 * C314                spring options, then grazing
```

Note the asymmetry in rows 4–6: established plants take the stage multiplier, but each **newly
emerged cohort takes `C167`** — the pre-emergent multiplier — because a pre-emergent is still
active in the soil when they come up. Miss that and nothing downstream is right.

### Closing the year

The stand that survives to spring sets seed, and how much depends on how crowded it is:

```
seed per plant = max_seed / (constant + C177 + crop_competitiveness * plant_density)
```

`C177` is not the raw plant count. It is a **competition-weighted density**: the plant cascade
re-run with each cohort scaled by how competitive it actually is. For dry or wet sowing those
weights run 1, 0.3, 0.1, 0.02 — a plant that emerged with the crop competes fully, one that came
up weeks later barely competes at all. Sowing later raises the later weights, because those
cohorts then emerge nearer the crop.

The `crop_competitiveness * plant_density` term is why a high seeding rate suppresses ryegrass: a
thicker crop leaves less room to set seed. Two phytotoxicity discounts follow — one if any
herbicide was used, one if any spring operation involved a spray.

Finally, harvest weed-seed control is applied **to the newly set seed only**. Seed already shed on
the ground never enters the header. What remains loses a fixed fraction over summer and becomes
next year's `D11`.

### Why control options are crop-specific

Topik controls 90% of ryegrass in wheat and nothing in canola. Rather than store a matrix of
option × crop lookups in every formula, the workbook does something neater: the activation cell
holds the **crop code**, not a boolean. One cell says both *whether* an option applies and *which
column* of the control table to read. That single trick is what `rim/activation.py` and
`rim/survival.py` are built around.

## 4. The block structure

The port proceeds one formula block at a time, in dependency order. Each block is a module, tested
against Excel independently before the next depends on it.

| Block | Excel range | Module | What it does |
|---|---|---|---|
| 1 | `Calcs` 184–189 | [`rotation.py`](rim/rotation.py) | Enterprise labels → the rotation key that Table 8 is indexed by |
| 2 | `Calcs` C7:C49 | [`activation.py`](rim/activation.py) | Strategy grid → which options are active, as crop codes |
| 3 | `Calcs` 55–97 | [`survival.py`](rim/survival.py) | Each active option → the fraction of ryegrass surviving it |
| 3b | `Calcs` C99, C164:C170 | [`stage_multipliers.py`](rim/stage_multipliers.py) | Per-option factors → seven per-stage multipliers |
| 4 | `Bio results` D3:D8, D11:D16 | [`population.py`](rim/population.py) | The two seasonal cascades |
| 5 | `Bio results` D17:D20 | [`seed_set.py`](rim/seed_set.py) | Seed production, and the carry to next autumn |
| 6 | `Bio results` D23:D50 | *not ported* | Yield and competition |
| 7 | `Eco results` E3:E59 | *not ported* | Revenue, costs, gross margin |

[`rim/calcs.py`](rim/calcs.py) composes blocks 1–5 into one year and iterates the ten.

Everything **not** in that table — `engine.py`, `ryegrass.py`, `seed_bank.py`, `yields.py`,
`economics.py`, `defaults.py` — is the original pre-port implementation. It still drives the
Streamlit app. It is not evidence-backed and should not be reasoned from. See
`.claude/memory/engine-port-status.md` for what is genuinely ported at any moment.

## 5. Parameters are generated, never typed

Hand transcription is where silent divergence enters. Every model parameter is extracted from the
workbook by [`tools/extract_params.py`](tools/extract_params.py) into `data/`, each file carrying
a `_source` header naming the workbook version, the ranges read, and — per value — the formula
that consumes it.

| File | Source | Contents |
|---|---|---|
| `calcs_survival_table.json` | `Calcs!N54:T97` | Ryegrass control by option × crop |
| `calcs_stage_constants.json` | `+Options!AG126:AG145`, `Calcs!N167` | Scalars folded into the multipliers |
| `calcs_table8.json` | `Calcs!C193:M291` | Yield, grazing control and stocking by rotation key |
| `germination.json` | `+Options` 105–109, 115–119 | Cohort germination fractions |
| `seed_set.json` | `+Options` 59–60, 87, 131–135 | Competition and seed production |
| `strategy_vocabulary.json` | `2.Strategy` D/P lists, `1.Profile!C14:C35` | Dropdown labels, stocked products |

Do not hand-edit these. Regenerate them:

```console
.venv\Scripts\python -m tools.extract_params
```

`data/defaults.json` is **not** in this scheme. It is pre-port, unread at runtime, and
deliberately untracked.

## 6. How Python is checked against Excel

This is the part that did not exist before and without which none of the rest is trustworthy.

### Two ways to ask Excel

**The cheap path.** openpyxl reads the values Excel cached the last time it recalculated and
saved. For the workbook's own stored scenario those are exact full-precision floats. No Excel
installation, works on any platform, runs in milliseconds.

**The full path.** [`tools/excel_oracle.py`](tools/excel_oracle.py) copies the workbook to a temp
directory, drives a hidden Excel instance with macros force-disabled, writes new inputs into
`2.Strategy!D4:M19`, calls `CalculateFullRebuild()`, and reads `.Value2` — never `.Text`, which
would bake display rounding into the result. Windows + Excel + `pywin32` only.

The cheap path is only trustworthy because of a round-trip guard:

```console
.venv\Scripts\python -m tools.excel_oracle --selftest
```

This recalculates the workbook without changing a single input and compares the result against
openpyxl's cache across every `EcoSum` and `TabSum` field, for all ten years, at 1e-6. It passes.
That is what licenses reading cached values as though they were computed.

### Fixtures

A fixture is a captured scenario: the exact inputs, the Excel outputs, the `Sheet!Cell` each value
came from, units, and explicit tolerances. Fixtures are committed, so `pytest` runs on machines
without Excel; they are regenerated on machines that have it.

Each fixture also carries a `reference` block holding Excel's own intermediates — rotation codes,
activation cells, survival factors, stage multipliers, the full `TabSum` table. That is what lets
a block be ported and tested **before** the blocks it depends on exist: feed it Excel's inputs,
check its outputs.

The four fixtures are chosen for coverage, not realism:

| Fixture | Purpose |
|---|---|
| `susceptible_2022_lorf` | The workbook's own saved 10-year strategy |
| `continuous_wheat_no_control` | Every control off — the population runs to its ceiling |
| `rotation_coverage` | Barley, legume, consecutive canola, all three pasture types |
| `survival_coverage` | Every control option the saved workbook never uses |

Between them, 35 of the 37 survival rows are exercised. The two that are not are the workbook's
own "empty slot for adding a…" placeholders, which appear in no dropdown and cannot be selected.
A test pins that exact boundary so coverage cannot quietly regress.

### Running the checks

```console
.venv\Scripts\python -m pytest -q                    # everything
.venv\Scripts\python -m tools.parity_report          # where and by how much it diverges
.venv\Scripts\python -m tools.capture_fixture        # re-capture the saved scenario
```

`pytest` gives pass or fail. `parity_report` prints a field-by-field, year-by-year table of Excel
against Python — that is the instrument to work with while porting.

To capture a new scenario, write a JSON file in `scenarios/` using the workbook's own labels and:

```console
.venv\Scripts\python -m tools.capture_fixture --scenario scenarios/<name>.json
```

## 7. Current state

Blocks 1–5 are ported. `rim.calcs.simulate_years()` runs the full ten years from the strategy grid
alone, and every cell of `TabSum` matches Excel to floating-point noise: **640 comparisons, worst
relative error 5.9e-16**.

That is a stronger claim than it may look. Years are joined only by the seed bank, so an error in
any year compounds into every year after it. A full-run match cannot be produced by a model that
is merely close.

**What remains.** Yield (`Bio results!D23:D50`) and economics (`Eco results!E3:E59`) are not
ported, and `rim/engine.py` — which the Streamlit app calls — is still the original
implementation. So the whole-model parity fixtures still fail, and will until those two blocks land
and the engine is rewired. The biology is right; the money is not yet.

Read [`rim/calcs.py`](rim/calcs.py) first — it is short and shows the whole shape. Then

docstring explains its block and cites the formulas it ports.
